## 1. Короткий ответ

**По uuid.** Тот же `client_uuid` с другим `client_trip_id` сольётся в ту же
строку, и хранимый `client_trip_id` при этом не изменится. Класса 04.07 здесь
нет. Ставь.

## 2. Доказательство

### 2.1 Уникальности — две частичные и взаимоисключающие

```
uq_trips_legacy               UNIQUE (device_id, client_trip_id) WHERE client_uuid IS NULL
uq_trips_vehicle_client_uuid  UNIQUE (vehicle_id, client_uuid)   WHERE client_uuid IS NOT NULL
```

Предикаты дополняют друг друга, поэтому строка попадает ровно под один индекс.
Для строки **с** uuid `client_trip_id` не несёт никакой уникальности вообще —
он там обычная колонка данных. Столкнуться по нему uuid-несущие строки не могут
физически.

### 2.2 Арбитр UPSERT выбирается по наличию uuid

`_upsert_trips` делит пачку на две группы и каждой даёт свой `ON CONFLICT`
(`app/routers/data.py`, `_conflict_args`):

```python
if has_uuid:
    return ["vehicle_id", "client_uuid"], table.c.client_uuid.isnot(None)
return legacy_cols, table.c.client_uuid.is_(None)   # (device_id, client_trip_id)
```

`index_where` передаётся явно, чтобы `ON CONFLICT` целился в нужный частичный
индекс. Группа с uuid идёт в `DO UPDATE` (слияние), группа без uuid — в
`DO NOTHING` (изоляция, Фаза 5).

### 2.3 `client_trip_id` иммутабелен после вставки

Проверил не по докстрингу, а интроспекцией самой клаузы на живом коде:
`_trip_update_clause` обновляет 22 колонки, и в их числе нет ни одной из:

```
client_trip_id · device_id · vehicle_id · client_uuid
started_at · start_odometer · start_soc · id
```

То есть при повторном приходе того же uuid с новым `client_trip_id` сервер
находит строку по `(vehicle_id, client_uuid)`, сливает агрегаты — и оставляет
`client_trip_id` тем, каким он был при первой вставке. Новой строки не
появляется, чужая не затрагивается.

Попутно: `device_id` там же, в иммутабельных. Значит и перепейринг устройства
твои строки не размножит.

## 3. Одно место, где ключом всё-таки `client_trip_id`

Честности ради: такой путь есть ровно один — `POST /v2/sync/uuid-mapping`,
разовый backfill C1, который навешивает `client_uuid` на **старые строки без
uuid**, находя их по `client_id`. Если вызвать его после восстановления, когда
номера переехали, он привяжет uuid не к тем строкам. Это буквально твой класс
04.07.

Сейчас это безопасно: **в каноне 0 строк с NULL-uuid** из 140, то есть эндпоинт
— no-op, привязывать нечего, а строки с уже проставленным uuid он рапортует как
`already_set` и не трогает. Просто не зови его после рестора, и всё.

К фоновым трипам это не относится вовсе: они рождаются с uuid и через
uuid-mapping не проходят.

## 4. Поправку про +186 принял

Понял: `extra.source` появляется в +186, ставите обе сборки вместе, а фоновая
поездка без `extra.source` — это сборка старше +186, а не расхождение. Спорить
не буду, у тебя виднее.

Последствие с моей стороны маленькое: такая поездка не будет исключена из #8 и
может дать **одну строку в сводке одним утром** — после вчерашней правки #8
замораживает разрыв сразу после единственного сообщения, потока не будет. А
если она заполнит существующую дыру, то наоборот, закроет её. Действий от тебя
не требуется, просто чтобы ты знал, что это не тревога.

## 5. Встречное: детерминированный uuid и инвариант #5

Тут прошу проверить одну вещь заранее, чтобы не выяснять по факту.

Инвариант #5 сверяет **временную метку, зашитую в UUIDv7**, со `started_at`
трипа; допуск 48 часов. Проверяются только uuid с версией 7 — регекс
`^[0-9a-f]{8}-[0-9a-f]{4}-7`, всё остальное пропускается молча.

Фоновый трип по определению собирается задним числом. Дальше зависит от того,
что у тебя лежит в первых 48 битах:

| Форма детерминированного uuid | Что сделает #5 |
|---|---|
| v7, timestamp = **начало окна** (старт поездки) | молчит, всё хорошо |
| v7, timestamp = момент сборки | сработает на каждой поездке, собранной позже чем через 48 ч |
| v7-шейп, но биты из хеша | сработает практически на всех |
| не-v7 (v5/v8 в ниббле версии) | пропустит по регексу, тоже хорошо |

Из твоей формулировки «выводится из источника и границ окна» похоже, что у тебя
первый вариант, и тогда всё чисто. Но если хеш размазан по всем битам с
сохранением семёрки в версии — попадём во вторую-третью строку.

Это неприятнее, чем #8: **#5 не самозамораживается**. В отличие от пропущенной
поездки, расхождение uuid↔время описывает строку, которую в принципе можно
починить, поэтому напоминание там намеренно повторяется каждую ночь. Утренняя
сводка начнёт звонить и не перестанет.

Два чистых выхода, оба на твоей стороне и оба дешёвые: держать в timestamp-битах
старт поездки, **либо** не притворяться v7 (взять v5/v8) — тогда #5 не станет
его даже смотреть. Скажи, какой вариант у тебя фактически, и если ни один — я
подстрою #5 со своей стороны, это правка одного условия.
