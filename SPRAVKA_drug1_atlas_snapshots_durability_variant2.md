## Ответы на твои 6 вопросов

**1. UNIQUE — да, ровно `(vehicle_id, client_uuid)`.**
Подтверждено на проде: `uq_atlas_snapshots_vehicle_uuid UNIQUE (vehicle_id,
client_uuid)`. Других уникальностей на таблице нет.

**2. Повтор того же `client_uuid` → тихий no-op. НЕ 409, НЕ update.**
Сейчас `ON CONFLICT (vehicle_id, client_uuid) DO NOTHING`; строка считается в
`duplicates`, ответ 200. Данные не теряются — «тихо» пропускается только точный
дубль уже существующей строки.

**3. Курсор `since` двигается и на UPDATE — да, автоматически.**
Триггер `bz5_assign_server_seq_lww` висит `BEFORE INSERT OR UPDATE` и штампует
`server_seq = nextval(...)` на обоих. Сегодня строка двигается только на INSERT
исключительно потому, что endpoint никогда не апдейтит. Механизм «UPDATE →
перештамп server_seq → строка заново едет в pull» уже работает для `trip_series`
и `atlas_reveals`. Для Варианта 1 это было бы бесплатно; в Варианте 2 не
используется.

**4. Вариант 1 на сервере дёшев, блокеров нет — но с поправкой по `updated_at`.**
CHECK на таблице нет вообще (только FK/PK/UNIQUE), триггер не мешает — помогает.
Это тот же приём, что уже задеплоен для `atlas_reveals`/`trip_series`: guarded
`DO UPDATE` + `_dedup_last` по арбитру, ~десяток строк.
**НО:** `updated_at` на провод добавлять НЕ надо. Серверный `updated_at` — это
LWW-часы, триггер перезаписывает их в `now()` на каждой записи, поэтому клиентский
`updated_at` был бы затёрт и как хранимый tie-breaker не выживет. И он не нужен:
правило `incoming.steady_seconds > stored → overwrite, else no-op` уже
коммутативно/идемпотентно/порядко-независимо; при точном равенстве `steady_seconds`
(один и тот же момент зрелости) keep-stored безвреден. Если очень хочется
тай-брейк — сравнивай по существующему `frozen_at`.
Скрытая цена V1: каждый 30-сек `_persist` растущей клетки перештампует
`server_seq` → строка каждый раз заново едет по pull (churn на телефоне, пока
клетка жива). В V2 этого нет.

**5. Вариант 2 безопасен на 100%.**
Никакого серверного предположения об уникальности `(session_uid, band_kmh,
temp_window_c)` нигде нет. Проверил весь серверный код: атлас фигурирует ТОЛЬКО в
двух ingest-эндпоинтах и в `_PULL_MODELS`. Ни агрегатов, ни витрин, ни подсчёта
покрытия/звёзд, ни экспорта, ни ретеншена, ни canon-чека для атласа на сервере
нет — сервер чистое хранилище по контракту. N снимков с одинаковыми
(session_uid, band, window) и разными `client_uuid` = просто N append-only строк.

**6. Рекомендация — Вариант 2.** Согласен с твоим склонением (см. §7).

## §7. Почему Вариант 2, а не 1

- **Достигает реальной цели.** Твой §2 сам показывает: настоящая защита —
  «немедленно в локальную БД». Облака в движении на ГУ нет ни в одном варианте
  (`synced_at` всех сегодняшних строк — через 54 c после холодного старта в
  Wi-Fi). Значит преимущество V1 «облако видит растущее значение» — фиктивно.
- **Сохраняет immutable append-only** → «conflict-free by construction» остаётся
  правдой, без merge-правила, без мутабельной строки, без pull-churn.
- **Ноль изменений сервера/миграции/контракта** → нет синхронного выката трёх
  сторон и риска молчаливого расхождения ГУ/телефона (твой же риск для V1).
- **Без потери информации.** 120-сек чанки несут `session_uid`+band+window →
  клиент всегда пере-агрегирует их в «клетку за всю сессию» на чтении (взвешенное
  по `steady_seconds` среднее тождественно — ты уже это доказал). V2 хранит
  БОЛЕЕ гранулярно и воспроизводит семантику V1 по требованию; V1 схлопывает и
  теряет под-структуру.
- **Инварианты не ломаются** — звёзды (`dedupSessionCount` по `session_uid`) и
  среднее (взвешенное по `steady_seconds`) ты уже прогнал.

Цена V2 — только UX (счётчик снимков ×3, появление вилки `lo…hi`) — вопрос к
владельцу, не к контракту.

V1 я взял бы только если серверу нужна одна каноническая «строка-клетка» для
серверного агрегата/витрины — а её по дизайну нет.
