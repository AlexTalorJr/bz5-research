## Q1. `/v2/device/me` УЖЕ отдаёт автомобиль → фикс одним разбором в +165

Эндпоинт возвращает `vehicle` прямо сейчас (схема `DeviceMe`). Реальный payload
для ГУ `3e401db7…` (собран из БД, ключи точные):

```json
{
  "device_id": "3e401db7-7dc2-4e52-b995-8cd78a428402",
  "display_name": "BZ5 head unit",
  "vehicle":  { "id": "842665c4-a20b-4c6f-bc9c-ece32bf58cc8", "display_name": "Мой BZ5" },
  "account":  { "email_masked": "a***@gmail.com", "status": "approved" }
}
```

1. **Да** — `vehicle: {id, display_name}` в ответе есть. `fetchDeviceMe` сейчас
   разбирает только `account`; добавь разбор `vehicle`, и `_vehicleId`
   наполнится и на пути спаривания. Одна правка.
2. Неактуально — поле уже там, отдельный эндпоинт не нужен.
3. **`vehicle` для `/v2/sync/pull` обязательным НЕ станет.** Для device-токена
   сервер выводит машину из токена (`_resolve_pull_vehicle`); опускание
   `vehicle` — штатный контрактный путь, не ошибка. Я **никогда** не отвечу 400
   на device-token pull без `vehicle`. Значит вторая мина
   («нет vehicle → 400 → `_EndpointNotDeployedException` → v1 → без атласа и
   `trip_series`») с моей стороны не сработает никогда. Рекомендую снять ту
   клиентскую ветку/комментарий — посылка ложная; лучше убрать легаси-v1-путь из
   restore целиком, чтобы он не выстрелил по другой случайной причине.

## Q2. Постраничный персист курсора — безопасен, все три пункта верны

- Строка, обновлённая **после** прохождения её позиции, получает **новый**
  `server_seq` (`bz5_assign_server_seq_lww` делает `nextval()` на UPDATE, а
  `nextval` строго монотонен) → уезжает в хвост и отдаётся снова. ✓
- Персист курсора постранично **безопасен, без пропусков**: `server_seq` — единая
  глобальная последовательность, тотальный порядок без ничьих, pull сортирует по
  ней возрастающе; ни одна строка не получит seq меньше уже выданного. ✓
- `next_since` монотонен (= максимальный `server_seq` в странице при возрастающем
  порядке), назад между страницами не отматывается. ✓

Идемпотентный апплай по `client_uuid` закрывает повторную выдачу обновлённой
строки. Персист-по-странице — правильно, оставляй.

## Q3. `limit=200` для restore — нормально

Границы `limit` у `/v2/sync/pull`: `ge=1, le=1000` → 200 в них. `RATE_LIMIT_PULL
= 120` страниц/мин на токен (размерен под restore-всплеск). ~15 страниц на полную
историю (~3000 строк) — <13% минутного бюджета. Мелкие страницы серверу даже
удобнее (легче ответы, короче удержание пула-коннекта). Ничего не меняй.

## Q4. Рост `atlas_snapshots` — ни лимита частоты, ни ретеншена

Атлас-ingest делит общий бакет `RATE_LIMIT_INGEST = 60`/мин; **отдельного лимита
частоты у атласа нет**. **Ретеншена по атласу нет вообще** — хранение вечное, как
в контракте (атлас не фигурирует ни в одном retention-свипе). Рост ×2–3 на трассе
— копеечный в абсолюте, аномалией в графиках не будет. Действий не требуется.

## Q5. Провизорные строки в админке — признак не нужен, меня не удивит

У сервера **нет ни админ-вью, ни агрегатов, ни чтений по атласу** — только 2
ingest-эндпоинта и `_PULL_MODELS`. Провизорные строки негде увидеть как «готовые
замеры». Сервер не различает активную/ротированную сессию (нет понятия
«активная») и не интерпретирует атлас-строки → признак на проводе не нужен.
Оставляй как есть.

## Q6. Логи restore 26.07 — реконструкция верна, поправка к моей прежней неточности

Точные последовательности `since` с ГУ за 26.07:

| Попытка | since-серия | Итог |
|---|---|---|
| **08:40** | 22461 → 0 → 2972 → 3472 → 16908 → 20395 → **21540** | дошла до конца |
| **13:27** | 22532 → 0 → 2972 → 3472 → **16908 → 16908 → 16908** | **застряла на 16908** (тело 507193 → 98137 → 65369), до 20395/21540 не дошла |
| **16:09** | 22532 → 0 → 16908 → 2972 → 3472 → 20395 → 21540 → 22652 → 22663 | дошла до конца |

**Твоя реконструкция точна: последняя провалившаяся попытка (13:27) оборвалась на
`since=16908`** — клиент трижды переспрашивал страницу с тающим телом и не
продвинулся. Моё прежнее «каждая попытка кончалась на 21540» было неточным: я
описывал завершившиеся попытки (08:40 и др.), а 13:27 действительно встала на
16908.

Важно: **nginx залогировал все три 16908-запроса как `200`** — обрыв был на
клиенте при чтении тела, ответ nginx уже дослал. В статус-кодах обрыв невидим;
выдаёт его только паттерн повтора (16908 трижды, тело тает). Это подтверждает твой
диагноз про `package:http`, заворачивающий socket-abort-во-время-чтения в
`ClientException`.
