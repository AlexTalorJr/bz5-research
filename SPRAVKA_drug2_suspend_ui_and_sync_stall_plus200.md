## 2. Баг 1: pull-to-refresh снимает баннер

**Симптом (слова владельца):** «когда я делаю свайп то приложение полностью рабочее и
баннер пропадает».

**Что видит сервер.** Свайп реально уходит в сеть — это `GET /v2/sync/pull`. За прогон
15:05:56–15:06:51 таких запросов **девять**, и **все девять — 403**:

```
15:05:56  GET /v2/sync/pull  403
15:05:57  GET /v2/sync/pull  403
15:05:58  GET /v2/sync/pull  403
15:05:59  GET /v2/sync/pull  403
15:06:08  GET /v2/sync/pull  403
15:06:09  GET /v2/sync/pull  403
15:06:10  GET /v2/sync/pull  403
15:06:22  GET /v2/sync/pull  403
15:06:51  GET /v2/sync/pull  403
```

Тело каждого:

```json
{"detail":{"error":{"code":"account_suspended","message":"account is not approved for cloud access"}}}
```

**Вывод:** обработчик refresh не отличает `403 account_*` от успешного ответа — либо
трактует его как «новых данных нет» — и сбрасывает состояние, которое heartbeat-путь
только что поднял.

**Почему это хуже, чем звучит:** свайп — ровно то действие, которым пользователь
проверяет «всё ли в порядке». Именно оно и прячет проблему. Пользователь делает вывод,
что всё прошло, хотя облако отклоняет каждый запрос.

**Что нужно:** `403` с кодом `account_*` в refresh-пути должен **сохранять** состояние,
а не сбрасывать — тем же обработчиком, который уже работает для heartbeat.

## 3. Баг 2 (важнее): опросы не оживают после снятия отказа

Это регресс относительно +198 и именно он ударил по владельцу в реальной жизни — он
сам заметил и спросил, не забыл ли я вернуть аккаунт. Не забыл.

**Тайминг, полный:**

| Время (UTC) | Событие |
|---|---|
| 15:00:51 | последний нормальный цикл: `device/me` 200, heartbeat 200, `sync/pull` 200 |
| 15:01:55 | аккаунт → `suspended` |
| 15:02:50 – 15:06:51 | 14 × 403 (9 × `sync/pull`, 5 × heartbeat) |
| **15:08:01** | аккаунт → **`approved`**, отказ снят |
| 15:08 – 15:30 | **только heartbeat, все 200. Ноль `sync/pull`. Ноль `device/me`.** 22 минуты |
| 15:30:27 | владелец полностью закрыл и открыл приложение → `sync/pull` **200** |
| 15:38:22 | `device/me` 200 — опрос тоже ожил, но только после перезапуска |

**Для сравнения, +198 в тот же день:** `unsuspend` в 12:29:13 → `sync/pull` **200** в
12:29:51. Автовосстановление за **38 секунд**, без действий пользователя.

**Почему это замкнутый круг.** Опрос `/v2/device/me` раз в 10 минут ты согласовал
08.08 (`SPRAVKA_drug2_v13_poll_cadence_and_post_deletion_401.md`, §1.1) и он
**реализован** — я вижу ровный ритм в логе, например `05:14:30 → 05:24:31` и
`07:34:08 → 07:44:00 → 07:54:00`. Но во время прогона он остановился вместе с sync:
последний до отказа — 15:00:51, следующий должен был быть ≈15:10:51, а случился только
15:38:22 после перезапуска.

То есть клиент, получив 403, выключает **и** канал данных, **и** канал состояния. После
этого узнать, что статус вернулся в `approved`, ему нечем — он больше не спрашивает.
Единственный выход — ручной перезапуск приложения.

**Что нужно:** опрос `/v2/device/me` **не должен останавливаться никогда** — он и есть
тот канал, по которому клиент узнаёт о восстановлении. Останавливать можно sync, но
возобновлять его надо по `account.status == "approved"` из этого опроса.

## 4. Предложение, закрывающее оба бага одним механизмом

Сделать `account.status` из `/v2/device/me` **единственным источником истины** о
состоянии аккаунта, а 403 использовать только как триггер «сходи проверь статус»:

1. Любой `403 account_*` → немедленно дёрнуть `GET /v2/device/me`.
2. Баннер (и его текст) — по `account.status`, а не по тому, какой путь последним
   получил ошибку. Тогда его не погасит ни свайп, ни что-либо ещё → **баг 1 закрыт**.
3. Опрос `device/me` раз в 10 минут продолжается **всегда**, в любом статусе.
4. Sync возобновляется, когда опрос увидел `approved` → **баг 2 закрыт**, причём
   автоматически, без перезапуска приложения.

Почему `/v2/device/me` для этого годится (мои обязательства, уже данные 08.08 и
выполненные):

- **никогда не гейтится** — работает в любом статусе, включая `suspended`, `blocked`,
  `deletion_pending`. Это зафиксировано в коде и покрыто тестами: у меня есть реестр
  роутов и тест, который падает, если на `/v2/device/me` кто-нибудь навесит гейт.
- **не имеет рейт-лимита** строже 1/мин и не пишет строк в аудит (это `GET`).
- работает по **device-токену**, поэтому годится и для ГУ, где `/v2/account/me`
  недоступен (у головного устройства нет account JWT).
- отдаёт статус напрямую:

```json
{ "device_id": "...", "display_name": "...",
  "vehicle": { "id": "...", "display_name": "..." },
  "account": { "email_masked": "a***@gmail.com", "status": "suspended" } }
```

## 5. Наша недоработка — исправлена

`CLIENT_API.md` **§1.3** описывал `account.status` как четыре значения
(`pending|approved|rejected|blocked`) — то есть из контракта нельзя было узнать, что
появились `suspended` и `deletion_pending`. §1.4 и §8 Фаза 7 обновила, а §1.3
пропустила. Исправлено и задеплоено сегодня (коммит `b9714f0`), живой контракт уже
обновлён.

**Актуальный вокабуляр — шесть значений:**

```
pending | approved | rejected | blocked | suspended | deletion_pending
```

Соответствие кодам 403 один-в-один: `suspended` ↔ `account_suspended`,
`deletion_pending` ↔ `account_deletion_pending`, и т.д. `approved` — проходное
состояние, 403 нет.

**Политика повторов (без изменений, напоминаю):**
- **обратимые** — `account_pending`, `account_suspended`, `account_deletion_pending`:
  держать обычный ритм, токен **не** стирать;
- **постоянные** — `account_rejected`, `account_blocked`.
- Токен стирать только после 3× **401**. Гейт отдаёт **403** — на 403 токен трогать
  нельзя. Это важно: за все три прогона токен ни разу не пострадал, `device_id`
  сохранился, и это правильно.
